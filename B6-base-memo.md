# Use Debian 13 for both images

**B6 recommendation for the owner's ruling, 2026-11-19.** Adopt Debian 13 (trixie) on amd64 and Debian live-build for the sitting stick and the node. Maintain one pinned Linux source tree with two project-owned kernel configurations and separate package lists. The stick excludes network and DVB drivers, Bitcoin Core and satellite software. The node can carry the drivers its receivers require. Debian's tooling accepts a custom kernel package directly. The main cost of this choice falls on the node team, which will need to build and qualify some satellite packages. Project basis: `design/DESIGN_refugium_os.md@c026b9b159:L110` and `design/DESIGN_refugium_os.md@c026b9b159:L127`. [Debian Live manual](https://live-team.pages.debian.net/live-manual/html/live-manual/customizing-package-installation.en.html)

## Where Nix earns its place

Keep Debian as the v1 image base and reuse the project's pinned Nix builds for individual tools. The wallet flake already defines a portable Linux `mr-gui` and a Nix-native one. Use the portable output as the first candidate on Debian and test it with the stick's display, folder picker and terminal. The engraving flake builds the project's patched `picotool`. Its executable and runtime dependencies can be included at their original store paths in the read-only image without running a Nix daemon on the stick. Record those paths and hashes in the image manifest. Any libraries shipped this way also need security updates when their Nix pins change. See refugium-wallet `flake.nix@5da720457b:L164` and mnemonic-engrave `flake.nix@8829885954:L30`. [Nix runtime closure queries](https://nix.dev/manual/nix/2.32/command-ref/nix-store/query)

NixOS is a credible alternative for both roles. Shared modules can describe the two configurations, image recipes and boot tests. The earlier wallet design explicitly specified a NixOS sitting image and a release-specific source archive for offline rebuilding. The newer OS design leaves B6 open, and the W2 spec assumes Debian in its terminal discussion. Record which image and offline rebuild commitments carry forward when ruling on B6. Building the same disk twice from identical Debian package files tests assembly. Rebuilding the shipped applications or the complete system from archived source is a separate claim. If maintaining the earlier end-to-end Nix release workflow is a primary requirement, I would favor NixOS. The Debian diagnostic has booted. A like-for-like NixOS image and a two-builder result for either base are still unmeasured. See refugium-wallet `design/SPEC_framework_slint.md@5da720457b:L1123`, `design/SPEC_w2_mr_gui_sitting.md@5da720457b:L257` and mnemonic-refugium `design/DESIGN_refugium_os.md@c026b9b159:L127`. [NixOS image builds](https://nix.dev/tutorials/nixos/building-bootable-iso-image.html) · [NixOS VM tests](https://nix.dev/tutorials/nixos/integration-testing-using-virtual-machines.html)

For the node I evaluated the top-level amd64 package names in the nixpkgs revision pinned by mnemonic-engrave (`a7868a727837`, source hash matched its lock). GNU Radio, RTL-SDR and TSDuck are present. Four specialised names were absent from that top level: `bitcoin-satellite`, `blockstream-satellite`, `gr-dvbs2rx` and `leandvb`. This identifies existing recipes; receiver hardware still requires qualification. [Pinned TSDuck recipe](https://github.com/NixOS/nixpkgs/blob/a7868a727837f3c09cee2ce0ca671c76b1589fed/pkgs/by-name/ts/tsduck/package.nix)

## The receiver packages decide the fallback

Debian 13 provides GNU Radio, RTL-SDR and DVB utilities. On 2026-11-19 its main amd64 index lacked five specialised packages, including `bitcoin-satellite`. Blockstream publishes all five for Debian 12 and Ubuntu 24.04. Its Debian 13 index returned HTTP 404. W5 should pin and build the required components against trixie, then test the S400, TBS and RTL-SDR receiver paths. If maintaining those native packages is unacceptable, **choose Ubuntu 24.04 LTS** and pin Blockstream's PPA separately. Package availability alone establishes neither driver compatibility nor reception. [Debian index](https://deb.debian.org/debian/dists/trixie/main/binary-amd64/Packages.xz) · [Blockstream Debian suites](https://aptly.blockstream.com/satellite/debian/dists/) · [Ubuntu receiver packages](https://ppa.launchpadcontent.net/blockstream/satellite/ubuntu/dists/noble/main/binary-amd64/Packages.gz)

Buildroot would make sense if a measured image-size limit dominated the decision. It also makes the project responsible for more of the toolchain, graphical stack and receiver packaging. For scale, Debian lists its stock 13.0 standard live image at 1.8G and Xfce live at 3.5G. Measure the finished Refugium image and peak RAM during a full sitting before specifying minimum media or memory. [Buildroot manual](https://buildroot.org/downloads/manual/manual.html) · [Debian image sizes](https://cdimage.debian.org/mirror/cdimage/archive/13.0.0-live/amd64/iso-hybrid/)

## Replace the stick from a verified image

For each release, pin both Debian and Debian Security snapshots, the builder, kernel source and configurations, and application inputs. Retain authenticated package metadata and package hashes. Apply kernel fixes to the shared source, rebuild both configurations and run each image's own acceptance tests. Require two clean builds to produce the same SHA-256 over the complete image before signing a manifest with the image role, version, byte count and hash. This is a release requirement; reproducibility of a Refugium image remains to be demonstrated. [Debian snapshots](https://snapshot.debian.org/) · [Linux reproducible builds](https://docs.kernel.org/kbuild/reproducible-builds.html)

For an update, verify the manifest signature against an independently obtained project key, verify the image hash, write a replacement stick, and check the written bytes over the declared image length. Keep the previous stick until the replacement boots. The sitting computer stays offline throughout. [Debian image verification](https://www.debian.org/CD/verify)
